# NSync Notes API: Client Description

Reference for the NSync note service: the PHP webservice that stores notes
uploaded by Pebble sync clients, and the server PebbleIndexSync talks to. It
should be enough to write a client against it without reading the server source.

---

## 1. Overview

NSync stores short plain-text notes as markdown files. Each request is
authenticated by a per-client token, and each token is confined to its own note
store: a token can only see and modify the notes in the store assigned to that
token. Whether two tokens share a store is up to the operator's configuration.

The API is five operations on a single endpoint:

| Operation | Request | Effect |
|---|---|---|
| Save | `POST /index.php` | Store a new note |
| List | `GET /index.php?action=list` | List this token's notes |
| Read | `GET /index.php?action=read&filename=...` | Fetch one note's full content |
| Delete | `GET /index.php?action=delete&filename=...` | Delete one note |
| Mark as read | `GET /index.php?action=markasread&filename=...` | Hide one note from this client's list (soft delete) |

Filenames are assigned by the server; titles may be supplied by the client or
generated by the server (section 10). A note's filename is the only identifier a
client needs, and it is returned by Save and by List.

---

## 2. Base URL and transport

- Base URL: `https://nsync.example.com/index.php`
- HTTPS only. Authentication travels in a request header, so plain HTTP must
  never be used.
- JSON appears **only in responses**; see the note in section 5: save
  requests are form submissions, not JSON.

---

## 3. Authentication

Every request to `index.php` must carry this HTTP header:

```http
Token: <your-token>
```

- The header name is `Token` (case-insensitive per HTTP, but use this spelling).
- The token is at least 6 characters long and is issued by the operator.
- The token selects the note store. Tokens assigned the same store share
  notes; tokens with different stores never see each other's notes.
- Missing, too-short, or unknown token → **HTTP 403 with an empty body**
  (no JSON). Clients must not attempt to parse a JSON body on 403.

Treat the token as a secret: never log it, never put it in a URL or query
string, never commit it.

---

## 4. Request and response conventions

- Responses that carry data are JSON encoded as UTF-8, with
  `Content-Type: application/json; charset=utf-8`.
- Responses that carry data also send `Cache-Control: no-store, private` and
  `Pragma: no-cache`. Responses are never cached.
- The single exception is the 403 refusal, which has an **empty body**.
- Save requests send form fields (`multipart/form-data` or
  `application/x-www-form-urlencoded`). List/read/delete/mark-as-read use
  query parameters.
- All timestamps in responses and in note frontmatter are ISO-8601
  `YYYY-MM-DDTHH:MM:SS` without a timezone offset, rendered in the server's
  configured timezone (`Europe/Berlin`). The only exception is `stored-at`,
  which is unix seconds (section 12).

---

## 5. Save a note

```http
POST https://nsync.example.com/index.php
Token: <your-token>
Content-Type: application/x-www-form-urlencoded
```

### Request fields

| Field | Required | Type | Description |
|---|---|---|---|
| `transcription` | yes | string | The note body. |
| `recordedAt` | yes | string | Client capture time, as **unix milliseconds** (an integer in milliseconds). Must contain digits only, no sign, decimal point, or internal spaces. |
| `client` | no | string | Device label used in the auto-generated title **only if** the token has no configured device name. Otherwise ignored. |
| `title` | no | string | Explicit note title. When present and non-empty, it is used (after normalization, see section 10) and no automatic title is generated. |

Notes:

- The body is trimmed (leading/trailing whitespace removed) before it is
  measured, hashed, and stored.
- `recordedAt` determines the note's `date` and `modified`; the server converts
  it to its configured timezone. Send the current epoch time in milliseconds to
  mean "now".
- **Send form fields, not a JSON body.** A JSON request body does not populate
  the form fields, so `transcription` is seen as empty and the call returns the
  `too_short` skip (HTTP 200, nothing saved) instead of an error. This is the
  single most common integration mistake.

### Validation order

The server evaluates in this exact order, and stops at the first match:

1. `transcription` is not a string (e.g. sent as an array) → `400 bad request`.
2. Trimmed body shorter than **8 characters** → `200 {"skipped":true,"reason":"too_short"}`.
3. Trimmed body longer than **20000 characters** → `413 note too large`.
4. `recordedAt` missing, empty, or not all digits → `400 bad request`.
5. A note with the same body (sha256 of the trimmed text) was already stored
   within the dedup window → `200 {"skipped":true,"reason":"duplicate","filename":"<existing>"}`.
6. Otherwise the note is stored → `200 {"filename":"<new-filename>"}`.

### Success response

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"filename":"202609100226.pftTsMaG.md"}
```

### Soft-skip responses (HTTP 200, nothing saved)

```json
{"skipped":true,"reason":"too_short"}
```

```json
{"skipped":true,"reason":"duplicate","filename":"202609100226.pftTsMaG.md"}
```

On `duplicate`, the returned `filename` is the existing (already stored) note.
Because an identical body is not stored twice within the dedup window, a retry
of the same note is safe and should be treated as success.

### Example request

```http
POST /index.php HTTP/1.1
Host: nsync.example.com
Token: YOUR_TOKEN
Content-Type: application/x-www-form-urlencoded

transcription=Buy%20milk%20and%20bread.&recordedAt=1789000000000&title=Weekly%20shopping
```

Equivalent `curl` invocation:

```sh
curl -sS -X POST 'https://nsync.example.com/index.php' \
  -H 'Token: YOUR_TOKEN' \
  -F 'transcription=Buy milk and bread.' \
  -F 'recordedAt=1789000000000' \
  -F 'title=Weekly shopping'
```

`1789000000000` milliseconds is `2026-09-10T02:26:40` in `Europe/Berlin`; the
example response filename above is derived from that capture time.

---

## 6. List notes

```http
GET https://nsync.example.com/index.php?action=list
Token: <your-token>
```

Returns a JSON array of this token's notes. The array is empty (`[]`) when the
token has no notes yet. Notes this client has marked as read (section 8) are
excluded.

### Response

```json
[
  {
    "filename": "202609100226.pftTsMaG.md",
    "date": "2026-09-10T02:26:40",
    "lastmodified": "2026-09-10T02:26:40",
    "title": "Weekly shopping"
  },
  {
    "filename": "202608211341.aB3dEf9h.md",
    "date": "2026-08-21T13:41:01",
    "lastmodified": "2026-08-21T13:41:01",
    "title": "Note Index Fri 21 Aug 13:41"
  }
]
```

| Field | Meaning |
|---|---|
| `filename` | Server-assigned identifier; use it for read, delete, and mark-as-read. |
| `date` | Note capture time from `recordedAt` (`YYYY-MM-DDTHH:MM:SS`). |
| `lastmodified` | Same source as `date`. |
| `title` | Stored title (client-supplied or auto-generated). |

---

## 7. Read a note

```http
GET https://nsync.example.com/index.php?action=read&filename=<filename>
Token: <your-token>
```

Returns the full markdown of one note, including its frontmatter, as a single
`content` string.

### Response

```json
{
  "content": "---\ntitle: \"Weekly shopping\"\ndate: 2026-09-10T02:26:40\nmodified: 2026-09-10T02:26:40\nstored-at: 1789000600\nhash: 9f2c...e1\n---\nBuy milk and bread.\n"
}
```

Decoded, `content` is:

```markdown
---
title: "Weekly shopping"
date: 2026-09-10T02:26:40
modified: 2026-09-10T02:26:40
stored-at: 1789000600
hash: 9f2c...e1
---
Buy milk and bread.
```

- `filename` must match the pattern in section 11. A missing or malformed
  `filename` → `400 bad request`; a filename that does not exist for this token
  → `404 not found`.
- A successful read also marks the note as synced on the server (an internal
  `last-sync` stamp). That stamp is **never** included in the returned `content`,
  so client-visible content stays stable across repeated reads. The internal
  `readby` line (section 8) is likewise never included.
- **Retention:** the `last-sync` stamp marks the note as pulled by a client.
  The server's garbage collector then deletes the note once its `stored-at`
  (section 12) is older than a configured number of days (7 days on the
  reference server). A client has to store the content locally when reading;
  re-reading or deleting a note days after it was read may return
  `404 not found`.

---

## 8. Mark a note as read (soft delete)

```http
GET https://nsync.example.com/index.php?action=markasread&filename=<filename>
Token: <your-token>
```

Hides one note from this client's `list` without deleting it (a "soft
delete"). The note stays in the store and can still be read or deleted by its
`filename`.

### Response

```json
{"ok": true}
```

- `filename` must match the pattern in section 11. A missing or malformed
  `filename` → `400 bad request`; a filename that does not exist for this token
  → `404 not found`.
- The server writes a frontmatter line `readby: <device>` on the note, where
  `<device>` is this token's device name simplified for safe frontmatter:
  lowercased, trimmed, alphanumeric characters only. `list` then skips notes
  whose `readby` matches this client's simplified device name.
- `readby` is internal bookkeeping: `read` responses never include it (like
  `last-sync`, section 7).
- A token without a usable device name (none configured) cannot mark notes as
  read → `400 bad request`.
- Marking a note that is already marked is idempotent: `200 {"ok":true}`.
- The mark only affects this client: other clients with different device names
  still see the note in their `list`. When the operator has assigned several
  tokens to the same store, each note remembers only the most recent `readby`
  device.

---

## 9. Delete a note

```http
GET https://nsync.example.com/index.php?action=delete&filename=<filename>
Token: <your-token>
```

### Response

```json
{"ok": true}
```

- Deleting is permanent and only affects this token's store. (Notes that were
  read are also removed automatically after the retention period, see section 7.)
- A missing or malformed `filename` → `400 bad request`; a nonexistent note →
  `404 not found`.

---

## 10. Title handling

A client may set the title explicitly with the `title` field. If it does not,
the server assigns a title as follows:

1. **Client-supplied `title`**: used (after normalization, see below) when
   non-empty. No automatic title is generated, and the optional model-based
   titling is skipped.
2. **Timestamp title**: `Note {device} {D j M H:i}` in the server timezone, for
   example `Note Index 01 Thu 10 Sep 02:26`. `{device}` is the token's configured
   device name, or the request's `client` field if no device name is configured.
   With neither, the device part is omitted: `Note Thu 10 Sep 02:26`.
3. **Model title (optional)**: if the operator has enabled the optional local
   model titling for this token and no `title` was supplied, the model may
   replace the timestamp title. Model titling always falls back to the
   timestamp title on any failure, so a note is never lost or rejected because
   of it.

A client-supplied `title` is normalized before it is stored: control
characters are removed, whitespace is collapsed to a single line, wrapping
quotes and a trailing period are stripped, and the result is capped at 120
characters. Do not depend on the exact generated title text when the model
title feature is enabled.

---

## 11. Limits, identifiers, and deduplication

| Item | Rule |
|---|---|
| Minimum body | 8 characters after trimming. Shorter → `200` `too_short` skip. |
| Maximum body | 20000 characters after trimming. Longer → `413`. |
| Body counting | Characters (UTF-8) when the `mbstring` extension is available, otherwise bytes. |
| Filename pattern | `YYYYMMDDhhmm.<8-alphanumeric>.md`, i.e. regex `^[0-9]{12}\.[A-Za-z0-9]{8}\.md$`, e.g. `202609100226.pftTsMaG.md`. Filenames are assigned by the server. |
| Dedup window | 14400 seconds (**4 hours**), keyed on the sha256 of the trimmed body and the server store time. |
| Dedup identity | Body only. The same text with a different `title` is still considered a duplicate within the window. |

Oversized requests: the server's PHP `post_max_size` limits the raw request
body. If a request body is large enough for PHP to drop the form fields, the
call returns the `too_short` skip rather than `413`. Keep note bodies well under
the maximum.

---

## 12. Note file format

Each note is a markdown file with a YAML frontmatter block followed by the
trimmed body:

```markdown
---
title: "Weekly shopping"
date: 2026-09-10T02:26:40
modified: 2026-09-10T02:26:40
stored-at: 1789000600
hash: <sha256 of the trimmed body>
---
Buy milk and bread.
```

| Key | Meaning |
|---|---|
| `title` | Stored title. Always a double-quoted scalar. |
| `date` | Capture time from `recordedAt`, in the server timezone. |
| `modified` | Same value as `date`. |
| `stored-at` | Server time of the save, as unix seconds. Reference for dedup and cleanup. |
| `hash` | sha256 of the trimmed body. |
| `last-sync` | Internal only. Added after a successful read; never returned to clients. Used by the server's garbage collector to delete synced notes after the retention period (section 7). |
| `readby` | Internal only. Written by `markasread`; contains the marking client's simplified device name. Never returned to clients; `list` uses it to hide marked notes (section 8). |

---

## 13. Error codes

All error responses except the 403 refusal carry a JSON body of the form
`{"error":"<message>"}`.

| HTTP | Body | Meaning | Typical cause |
|---|---|---|---|
| 200 | `{"filename":"..."}` | Note saved. | none |
| 200 | `{"skipped":true,"reason":"too_short"}` | Nothing saved: body too short. | Trimmed body under 8 chars, or fields not received. |
| 200 | `{"skipped":true,"reason":"duplicate","filename":"..."}` | Nothing new saved: duplicate body. | Same body already stored within 4 hours. |
| 200 | `{"ok":true}` | Note deleted, or marked as read. | none |
| 400 | `{"error":"bad request"}` | Malformed request. | Invalid `recordedAt`; `transcription` not a string; missing/malformed `filename`; `markasread` with no usable device name; HTTP method other than GET or POST. |
| 403 | _(empty)_ | Request refused. | Token missing/short/unknown; `GET` without a valid `action`. |
| 404 | `{"error":"not found"}` | Note does not exist. | Read/delete/mark-as-read of an unknown `filename`, or of a synced note that was garbage-collected (section 7). |
| 413 | `{"error":"note too large"}` | Body over the maximum. | Trimmed body over 20000 characters. |
| 500 | `{"error":"storage unavailable"}` | Server-side failure. | Storage write failed; retry later. |

Notes on specific codes:

- **403** is the only response with no body. It means the request was not
  authenticated (or a `GET` had no valid `action`). Do not parse JSON.
- **400 for methods**: any HTTP method other than `GET` or `POST` on
  `index.php` returns `400 bad request`.
- **200 is not proof of a save.** A successful save always includes a
  `filename` and does not include `skipped`. Always inspect the body.
- **500 on delete**: a delete whose filesystem unlink fails returns `500` with
  body `{"error":"not found"}` (not the usual `storage unavailable`). Treat any
  500 as a transient server-side failure.

## 14. Suggested client flow

### Save

1. Build the form with `transcription` (trimmed, 8–20000 chars) and
   `recordedAt` (current unix milliseconds as digits), plus optional `client`
   and `title`.
2. `POST` to `index.php` with the `Token` header and a form content type.
3. On `200`:
   - if the body has `filename` and no `skipped` → saved (keep the filename);
   - if the body has `skipped` → not stored; treat `"reason":"duplicate"` as
     success (the note already exists) and `"reason":"too_short"` as a
     client-side input problem.
4. On `400`/`413` → fix the request (bad `recordedAt`/filename, or body too
   large).
5. On `403` (empty body) → authentication problem; check the token.
6. On `500` → transient server failure; retry later.

### List / read / delete / mark-as-read

1. Send the `Token` header. For read/delete/mark-as-read, include a valid
   `filename` from `list`.
2. `200` → parse JSON (`[]`, a list of note objects, a `content` object, or
   `{"ok":true}`).
3. `403` (empty) → authentication problem; `400` → malformed `filename`;
   `404` → unknown note (including synced notes the server has since deleted,
   see section 7).

Idempotency: because identical bodies are not duplicated within 4 hours, a
retried save of the same note returns `duplicate` instead of creating a second
note. After the window expires, an identical body will be stored again, so only
retry genuine failures.

## Appendix A. Debug capture endpoint (not for clients)

`https://nsync.example.com/debug.php` is a separate, **unauthenticated** capture
endpoint used during device payload discovery. It isn't part of the client API
and shouldn't be used by client implementations.

- Any HTTP method is accepted; it writes a request dump to disk.
- When disabled (or if capture is off), it returns `404` with an empty body.
- When enabled, it returns `200 {"ok":true,"saved":"<dump-filename>"}`.
- It requires no token, and dumps may contain sensitive data.

Leave it alone in client code; it may be turned off at any time.
